
1) WORKFLOW1: Intelligent Advisor Matching

   Title: Smart Supervisor-Student Matching Workflow

   Description:
   This workflow covers the end-to-end process by which a student finds and
   requests a suitable FYP supervisor through the platform's intelligent
   matching system. It includes profile setup, preference input, algorithm-
   driven recommendations, request submission, and supervisor acceptance
   or rejection.

   Actors:
   - Student (primary)
   - Supervisor
   - System (matching algorithm)

   Preconditions:
   - Student has registered and logged into the platform.
   - Supervisors have registered, completed their profiles (expertise areas,
     research interests, available slots), and are marked as available.
   - Administrator has configured the current academic session/semester.

   Workflow Steps:

   Step 1 - Student Completes Project Profile
     1.1  Student logs in and navigates to "Start New Project" from the dashboard.
     1.2  Student fills in the Project Interest Form:
          - Project title (working title)
          - Project domain (e.g., AI/ML, Web Development, Cybersecurity,
            Data Science, IoT, Mobile Development, etc.) — selected from
            a predefined list with option to add custom tags.
          - Required skills/technologies (e.g., Python, React, TensorFlow,
            etc.) — multi-select with autocomplete.
          - Brief project description (150–500 words).
          - Preferred supervision style (e.g., weekly meetings, bi-weekly
            meetings, flexible/as-needed).
     1.3  Student submits the form. System validates all required fields and
          saves the project profile.

   Step 2 - System Generates Supervisor Recommendations
     2.1  Upon submission, the system runs the matching algorithm which
          evaluates supervisors based on:
          - Domain alignment: How closely the supervisor's research areas
            match the student's selected project domain (weighted highest).
          - Skill overlap: Percentage of required skills that fall within the
            supervisor's listed expertise.
          - Availability: Number of remaining open slots the supervisor has
            for the current semester (supervisors at full capacity are excluded).
          - Workload balance: Preference given to supervisors with fewer
            current advisees to promote fair distribution.
          - Supervision style compatibility: Match between student preference
            and supervisor's stated availability pattern.
     2.2  The system generates a ranked list of recommended supervisors,
          each with a match score (displayed as a percentage or rating).

   Step 3 - Student Reviews Recommendations
     3.1  Student is presented with the "Recommended Supervisors" page
          showing a ranked list of matched supervisors. For each supervisor,
          the following is displayed:
          - Supervisor name and department
          - Profile photo
          - Research interests and expertise areas
          - Match score with breakdown (domain match %, skill overlap %,
            availability status)
          - Number of available slots remaining
          - Past project titles supervised (if any)
          - Average student rating (from previous advisees, if available)
     3.2  Student can click on any supervisor to view their full profile,
          including a detailed bio, published work, and list of current/past
          FYP students.
     3.3  Student can filter and sort the list by:
          - Match score (default: highest first)
          - Domain
          - Available slots
          - Department
     3.4  Student can also use a manual search bar to search for a specific
          supervisor by name or expertise keyword if they want to go beyond
          the recommendations.

   Step 4 - Student Sends Supervision Request
     4.1  Student selects a preferred supervisor and clicks "Request Supervisor."
     4.2  A request form appears where the student provides:
          - A brief message to the supervisor explaining why they are a
            good fit (required, 50–300 words).
          - Attached project interest form summary (auto-populated from
            Step 1).
     4.3  Student submits the request. The system:
          - Records the request with status "Pending."
          - Sends an in-app notification and email alert to the supervisor.
          - Displays a confirmation message to the student: "Your request
            has been sent. You will be notified once the supervisor responds."
     4.4  Student may send up to 3 supervision requests simultaneously to
          different supervisors (configurable by admin). The system enforces
          this limit and displays remaining request count.

   Step 5 - Supervisor Reviews and Responds to Request
     5.1  Supervisor logs in and sees new request(s) on their dashboard
          under "Pending Requests."
     5.2  Supervisor clicks on a request to view:
          - Student's name, program, and academic details
          - Project title, domain, description, and required skills
          - Match score and compatibility breakdown
          - Student's message/motivation
     5.3  Supervisor chooses one of the following actions:
          a) Accept — Supervisor agrees to supervise the student.
             - System updates the request status to "Accepted."
             - Student receives an in-app notification and email:
               "Your supervision request has been accepted by [Supervisor Name]."
             - All other pending requests from this student to other
               supervisors are automatically withdrawn and those supervisors
               are notified.
             - Supervisor's available slot count decreases by one.
             - The student-supervisor pairing is recorded in the system.
          b) Reject — Supervisor declines the request.
             - Supervisor provides a brief reason (optional but encouraged).
             - System updates the request status to "Rejected."
             - Student receives a notification: "Your request to [Supervisor
               Name] was not accepted. Reason: [if provided]. You may send
               a new request to another supervisor."
             - Student's active request count is decremented, allowing them
               to send a new request.
          c) Request More Info — Supervisor asks for clarification.
             - Supervisor types a message/question for the student.
             - System updates request status to "Info Requested."
             - Student receives a notification and can reply via the
               platform's messaging interface.
             - Once the student responds, the supervisor can then Accept
               or Reject.

   Step 6 - Matching Finalized
     6.1  Once a supervisor accepts, the student-supervisor pair is formally
          established in the system.
     6.2  Both parties are redirected to a shared "Project Workspace" where
          they can:
          - Begin the proposal submission workflow (Workflow 2).
          - View each other's contact details and schedule.
          - Access a shared timeline and milestone tracker.
     6.3  The administrator dashboard is updated to reflect the new pairing
          and current allocation statistics.

   Postconditions:
   - Student is matched with a supervisor and the pairing is recorded.
   - Supervisor's available capacity is updated.
   - Both parties have access to the shared project workspace.
   - All other pending requests by the student are withdrawn.
   - The system's workload distribution statistics are updated.

   Exception/Alternate Flows:

   E1 - No Suitable Matches Found:
        If the algorithm finds no supervisors with a match score above the
        minimum threshold, the student is shown a message: "No strong matches
        found. Try broadening your project domain or adjusting required skills."
        The student can edit their project profile and re-run matching.

   E2 - All Requests Rejected:
        If all of the student's requests are rejected, the system notifies
        the student and suggests re-running the matching algorithm or
        contacting the department administrator for manual assignment.

   E3 - Supervisor Reaches Full Capacity Mid-Process:
        If a supervisor's slots fill up while a request is pending, the
        system automatically withdraws the pending request and notifies
        the student: "[Supervisor Name] is no longer available. Please
        select another supervisor from your recommendations."

   E4 - Request Timeout:
        If a supervisor does not respond within a configurable time period
        (default: 7 days), the system sends a reminder. After a second
        period (default: 3 more days), the request is auto-expired and
        the student is notified to select another supervisor.


2) WORKFLOW2

WORKFLOW2: Multi-Stage Proposal Submission & Approval

Title: Structured Proposal Submission, Feedback, Revision & Approval Workflow

Description:
This workflow describes how a student submits an FYP proposal inside the platform, receives supervisor feedback, iterates through revisions (multi-version), and finally gets administrative approval (or rejection). It supports an audit trail of proposal versions, clear status states, and automated routing/notifications.

Actors:
Student (primary)
Supervisor
Administrator
System (workflow engine + notifications)

Preconditions:
Student has an accepted supervisor pairing and both have access to the shared Project Workspace (from Workflow 1).
Administrator has configured the current academic session/semester and enabled proposal submission.
Supervisor is marked as “Active” and eligible to review proposals.

Workflow Steps

Step 1 — Student Creates Proposal Draft
1.1 Student opens the Project Workspace and navigates to Proposal > Create / Submit Proposal.
1.2 System displays a proposal template with required sections (example structure):
Title
Abstract / overview
Problem statement
Objectives
Proposed methodology
Tools/tech stack
Timeline / milestones (initial)
References
1.3 Student fills in the template and clicks Save Draft.
1.4 System validates required fields and stores it as:
Version v0.1 (Draft)
Status: Draft (Not Submitted)

Step 2 — Student Submits Proposal to Supervisor
2.1 Student clicks Submit to Supervisor.
2.2 System performs submission checks:
Required fields complete
Word count / page limits (if configured)
Plagiarism check (optional, configurable)
2.3 System locks the submitted version (read-only) and creates:
Version v1.0
Status: Submitted to Supervisor
2.4 System notifies the supervisor (in-app + email):
“New proposal submitted by [Student Name] for review.”

Step 3 — Supervisor Reviews and Responds
3.1 Supervisor opens Pending Proposal Reviews on their dashboard.
3.2 Supervisor views:
Proposal content (v1.0)
Student details + project profile summary
Commenting interface (inline comments + overall feedback)
3.3 Supervisor chooses one action:
a) Approve for Admin Review
Status becomes: Supervisor Approved
System routes proposal to admin queue
Student is notified: “Supervisor approved your proposal. Sent for admin review.”
b) Request Revisions (Most common)
Supervisor adds feedback (required) and optionally sets a revision deadline
Status becomes: Revisions Requested
Student is notified with feedback summary and deadline (if any)
c) Reject Proposal
Supervisor provides a reason (required)
Status becomes: Supervisor Rejected
Student is notified and allowed to create a new revision submission (fresh attempt)

Step 4 — Student Revises and Resubmits (Version Tracking Loop)
4.1 If Revisions Requested, student edits and saves changes.
4.2 System forces a Change Summary field (e.g., “What did you improve?”).
4.3 Student clicks Resubmit to Supervisor.
4.4 System creates a new locked version:
v1.1, v1.2, v2.0, etc. (depending on your numbering scheme)
Status: Resubmitted to Supervisor
4.5 Repeat Step 3 until supervisor approves or rejects.

Step 5 — Admin Reviews Proposal Decision
5.1 Admin opens Proposal Approval Queue.
5.2 Admin views:
Latest version
Supervisor decision + feedback trail
Version history + timestamps
(Optional) rubric/criteria checklist for proposal quality
5.3 Admin chooses one action:
a) Approve Proposal
Status: Admin Approved (Final)
Student & supervisor notified
System unlocks Milestone Tracking & Evaluation module (Workflow 3)
b) Request Revisions (Admin-level)
Admin adds comments (required)
Status: Admin Revisions Requested
Student notified; supervisor also informed (visibility)
c) Reject Proposal
Reason required
Status: Admin Rejected
Student must submit a corrected/new proposal version (policy configurable)

Step 6 — Proposal Finalization & Lock
6.1 When Admin Approved:
Proposal is marked as the approved baseline
System timestamps approval and stores final PDF snapshot
6.2 The Project Workspace updates with:
“Approved Proposal” badge
Activated timeline + evaluation features (Workflow 3)

Postconditions
Proposal has a final status: Admin Approved, Rejected, or Revisions Requested.
All proposal versions and feedback are stored with a complete audit trail.
Once approved, the system enables progress tracking and evaluation.

Exception / Alternate Flows
E1 — Supervisor Non-Response Timeout
If supervisor doesn’t respond within X days (configurable), system sends reminders.
After Y days, system escalates to admin for intervention.
E2 — Excessive Revision Attempts
After N revision cycles (configurable), system flags the case to admin for manual review.
E3 — Student Submits Without Required Sections
System blocks submission and highlights missing fields.
E4 — Session Deadline Reached
If proposal submission deadline passes, system prevents submission and prompts admin override if needed.


3) WORKFLOW3:

WORKFLOW3: Milestone Tracking, Meetings, Evaluation & Final Grading

Title: Integrated Milestone Tracking & Rubric-Based Evaluation Workflow

Description:
This workflow covers how the platform manages project progress after proposal approval: defining milestones, tracking submissions and meetings, collecting supervisor evaluations using rubrics, and producing final grading/analytics.

Actors:
Student (primary)
Supervisor
Administrator
System (tracker + notifications + analytics)

Preconditions:
Student-supervisor pairing exists (Workflow 1 completed).
Proposal is Admin Approved (Workflow 2 completed).
Admin has configured:
Milestone structure (or allowed custom milestones)
Evaluation rubrics + weightings
Submission deadlines and grading policy

Workflow Steps

Step 1 — System Creates Project Timeline (Milestone Plan)
1.1 After proposal approval, system opens Milestones tab in Project Workspace.
1.2 System either:
Option A (Standardized): Preloads department milestone template (e.g., Proposal, Literature Review, Prototype, Mid Review, Final Report, Viva).
Option B (Custom): Allows supervisor/admin to create milestones manually.
1.3 Each milestone includes:
Title
Description / deliverables
Due date
Required submission type (file upload/link/text)
Evaluation rubric (if applicable)
1.4 Student and supervisor receive notification:
“Project milestones have been activated.”

Step 2 — Student Works & Submits Milestone Deliverables
2.1 Student opens the active milestone and clicks Submit Deliverable.
2.2 Student uploads files and/or enters:
Deliverable link (Git repo, demo link)
Notes / progress summary
2.3 System validates submission format and timestamps it:
Status: Submitted
2.4 System notifies the supervisor:
“Milestone submission received for [Milestone Name].”

Step 3 — Supervisor Reviews Progress & Logs Feedback
3.1 Supervisor opens milestone submission.
3.2 Supervisor can:
Give quick feedback (comments)
Request resubmission (if policy allows)
Mark as accepted for that milestone
3.3 System updates milestone state:
Accepted / Needs Changes / Overdue (auto)
3.4 Feedback is stored as milestone history.

Step 4 — Meeting Scheduling & Attendance Log
4.1 Student or supervisor clicks Schedule Meeting inside workspace.
4.2 System shows available slots (simple availability input or calendar integration if later added).
4.3 Meeting is created with:
Date/time
Agenda
Mode (in-person/online)
4.4 System sends notifications to both parties.
4.5 After meeting, supervisor (or both) logs:
Attendance
Summary notes
Action items
Next meeting date suggestion
4.6 System links meeting notes to timeline for transparency.

Step 5 — Rubric-Based Evaluations (Midpoints and Final)
5.1 For evaluation milestones (e.g., Mid Review / Final), supervisor opens Evaluate.
5.2 System displays rubric with criteria, levels, and weights (configured by admin).
5.3 Supervisor enters:
Scores per criterion
Strengths / weaknesses comments
Recommended next steps
5.4 System calculates:
Milestone grade (if weighted)
Running total (if continuous assessment is enabled)
5.5 Student receives:
Score + rubric breakdown + written feedback

Step 6 — Admin Oversight & Final Grading
6.1 Admin dashboard shows:
Project progress status (on-track / at-risk / overdue)
Supervisor workload + evaluation completion rates
Grade distribution analytics
6.2 Admin can:
Request justification for extreme grades (optional policy)
Lock grades after submission deadline
Generate final grade reports
6.3 System finalizes:
Final grade (overall)
Completed rubric records
Project completion status: Completed / Incomplete / Deferred

Postconditions
Milestones, submissions, meeting logs, and evaluations are recorded.
Student receives structured feedback continuously.
Rubric-based grading is standardized and auditable.
Admin has visibility into allocations, progress, and outcomes.

Exception / Alternate Flows
E1 — Missed Milestone Deadline
System marks milestone as Overdue and notifies student + supervisor.
Admin is notified if overdue exceeds a threshold (e.g., 7 days).
E2 — Resubmission Allowed
If supervisor marks “Needs Changes,” system reopens milestone with a new due date window (policy-configurable).
E3 — Supervisor Unavailable / Reassignment
If supervisor becomes inactive, admin reassigns supervisor.
System preserves all milestone/evaluation history and transfers workspace access.
E4 — Academic Misconduct / Plagiarism Flag (Optional Module)
If plagiarism tool flags a deliverable, system locks it for admin review before evaluation.
